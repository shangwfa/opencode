# data-table 最佳实践审核（结合实际场景）

日期：2026-10-14。基于当前代码（含多向量化策略、searchFields、零相关过滤、OpenRouter 适配）与本日全部实测。
本报告只审核，不修改业务代码。结论以代码位置和实测为依据；未验证的项明确标注。

## 1. 结论

**当前实现适合：可信内部环境、数据量小到中等、允许人工校验结果的试点。**
**当前实现不符合生产级最佳实践。** 主要缺口是索引流水线可靠性、索引身份隔离、行级结果语义、质量基线，以及权限与租户边界。

这不是否定已完成的工作。多向量化策略、混合检索执行路径、零相关过滤、字段边界序列化已经解决了本日定位的核心问题。下面列出的是剩余风险。

## 2. 三个实际场景的符合度

| 场景 | 实际需求 | 当前能力 | 证据 | 判定 |
|---|---|---|---|---|
| RPA 指令检索（"哪个指令能完成某操作"） | 按指令名/描述找指令，语义同义改写可命中 | field 策略下 semantic 同义改写命中（"把页面上的表格搬到变量里"→提取表格数据） | openrouter-semantic 实测 S1/S3/S5 | 基本可用；需要质量基线 |
| OpenAPI 接口发现（"哪个接口能做某事"） | 按 summary/description 找接口，结果是接口而非片段 | row 策略整行向量；S4 "用户怎么登录系统" top1 误排 | 字段级探针：行内最高字段分数 max 聚合即可纠正 | 排序不稳定；需行级聚合（F07） |
| CSV/订单查询（"华东区已付款订单"） | 结构化过滤 + 数值范围 + 关键词 | keyword/filter/组合可用；数值范围不可用；无导入链路 | realdata C5/C6 通过；C20 观察（金额>50000 不可表达） | 过滤能力不足；导入依赖外部适配 |

## 3. 逐项对照最佳实践

严重度：**H** 阻断生产；**M** 影响正确性或体验，需排期；**L** 可接受的技术债。

### 3.1 索引流水线可靠性（H）

- 写入顺序：`insertRowsFromMetadataBatch` 先 `COMMIT` 行数据（database.service.ts:687），再在请求内同步调用 embedding（:720）。embedding 失败时行已落库、向量缺失，且只能靠调用方重试，重试会生成新 rowId（:602）造成重复行。
- 更新路径同步重算：`updateDatabase` 删列或换策略后 `await this.revectorizeAllRowsInDataset`（:379），全表读入内存后在请求内逐批调用 embedding。数据量大时会超时，且没有进度与断点。
- 没有索引任务表、没有租约、没有 outbox。已在代码中确认（`index_job` / `outbox` / 租约关键字均不存在）。
- 多 pod 下没有任务归属，无法保证"提交即索引"。

最佳实践：行写入与索引任务同事务写入，模型调用放在事务外，worker 通过租约领取，按版本发布，失败可重试且幂等。

### 3.2 索引身份与隔离（H）

- 物理索引名仍由 `getKnowledgeBaseIndexName(id)` 从用户 id 推导（database.service.ts:184）。`A-B` 与 `a_b`、`orders` 与 `kb_orders` 会映射到同一向量表。
- `index-identity-audit.ts` 只能扫描发现冲突，不能阻止新冲突。当前注册表中 0 冲突，是因为数据量少，并不说明机制安全。
- 冲突的后果是跨数据集向量混入、删除一个数据集时误删另一个的向量。

最佳实践：服务端生成不可变 storageId，物理名由 storageId 派生，与用户可见 id 解耦；注册表唯一约束兜底。

### 3.3 行级结果语义（M，直接影响 OpenAPI 场景）

- 检索单位是 chunk。一行多个字段或多个 chunk 会重复占用 topK。
- field 策略下 keyword 结果是向量级：实测"网页"6 行对应 7 个向量（B7）。
- 没有行级聚合，因此字段分数无法合成行分数。S4 类排序问题（row 策略整行向量误排）只能通过 field 策略 + max 聚合纠正，而聚合尚未实现。

最佳实践：先按 rowId 聚合（max 或加权），再裁剪记录 topK；chunk 与字段作为匹配证据返回。F07 是当前最值得优先做的检索改进。

### 3.4 相关性阈值（M）

- 默认 `minScore=0`（database-rows-search.ts:212），只过滤 cosine 恰好为 0 的结果。
- 真实 embedding 下几乎所有文本对都有非零相似度。实测"量子纠缠"等无关查询仍返回 3 条，top1 分数 0.089（S8）。
- 仓库已有 `MIN_RELEVANCE_SCORE = 0.2`，但 data-table 未启用。

最佳实践：阈值必须与 embedding 模型相关，并以评估集标定，不能用 0 作为"零相关"的代理。建议建立 L2 基线后再确定默认值。

### 3.5 向量化策略与成本（M）

- row / field / row+field 三种策略已实现，策略为数据集级配置，切换会重建。
- field 策略的向量数 = 行数 × 非空字段数。16 行 × 4 字段 = 64 个向量，没有成本预估，也没有上限。
- 字段权重不做（决策见优化方案）。这是正确的，但仅限于收益未证明的前提下。

### 3.6 数据模型与类型（H，直接影响 CSV 场景）

- 所有列类型为 TEXT（`mapSqlType` 恒定返回 TEXT）。`DATABASE_COLUMN_TYPES` 枚举存在，但请求 schema 没有 type 字段。
- 金额、数量、日期无法做范围比较。实测 C20 确认"金额>50000"不可表达。
- 无字段显示名、无来源列映射，中文表头需要调用方改名。

最佳实践：类型化列或原始 JSONB + 类型化投影；数值与日期可比较；来源映射与内部安全 key 分离。

### 3.7 安全与权限（H，若对外暴露）

- 路由层没有认证中间件，只有 `cors()`（app.ts:26），CORS 允许所有来源。
- 没有租户维度。数据集 id 即访问凭证。
- 已知的 `DROP/SET` 标识符问题已修复，但参数化与标识符白名单是本模块做得较好的部分。

前提：若网关负责认证与租户隔离，这一项可降级为 M。本次审核没有验证网关配置，因此不据此断言生产安全。

### 3.8 质量评估与可证明性（H）

- 目前没有 L2 召回评估集。mock 测试证明的是机制，不是质量。
- 真实 embedding 只有 3 个同义改写样本，加上 2 个 OBSERVE（S2、S4）。这不足以支持"语义检索质量达标"的结论。
- 按 rag 的 evaluation-rubric 体系，需要：代表性查询集、人工标注相关性、MRR/nDCG 基线、同义/歧义/精确三类分层。

### 3.9 测试与工程卫生（M）

- `bun test --isolate`（项目标准命令）：73 通过。
- 不隔离运行时，`openrouter-embedding.test.ts` 失败：`.env` 被 bun 自动加载，并且模块 mock 与环境变量在文件之间泄漏。这是测试卫生问题，不是功能问题，但说明测试依赖隐式环境。
- 端到端脚本是 zsh 文档脚本，依赖 docker exec psql，不能直接进 CI。需要转为可复用的测试套件。

### 3.10 可观测性与执行信息（做得较好）

- 响应包含 `execution`：有效策略、两路召回数、是否融合、字段限定、向量策略。
- 慢查询与检索阶段耗时有 profile 日志（`DB_ROWS_SEARCH_PROFILE`）。
- 对应最佳实践中"可解释检索"的要求，这一项基本符合。

### 3.11 API 契约一致性（L）

- 成功响应统一为 `{code, success, message, data}`，符合现有约定。
- 错误映射不一致：`POST /rows` 对不存在的数据集返回 400，其他行接口返回 404（已记录为观察）。
- 零权重、全零权重、增强组合不支持，均显式 400，符合"不静默替换"的原则。

## 4. 做得符合最佳实践的部分

- 向量存储选型：PostgreSQL + pgvector HNSW，与现有基础设施一致，避免引入新的状态存储。
- 混合检索：两路真实执行，融合后恢复原生绝对分数，单路失效时降级并标注。
- 参数化 SQL 与标识符白名单，字段名经过正则校验。
- 检索计划对外可见（execution）。
- 字段边界序列化，消除了 join('') 导致的跨字段粘连与数值粘连。
- 存量迁移使用 `ADD COLUMN IF NOT EXISTS`，策略切换有对应的重建。

## 5. 优先级建议

按"阻断生产 → 影响正确性 → 体验"排序：

1. **索引流水线可靠性**（3.1）：行与索引任务同事务写入，异步 worker，租约，幂等。这是生产化的前提。
2. **索引身份隔离**（3.2）：storageId 替代 id 推导名称；存量冲突先隔离再重建，不直接删除。
3. **质量基线**（3.8）：建立代表性查询集与评估指标，再决定阈值（3.4）与字段权重是否值得做。
4. **行级聚合 F07**（3.3）：解决 OpenAPI 场景的排序问题，同时修复 keyword 向量级重复。
5. **类型化列与数值范围**（3.6）：CSV 场景的结构化查询能力。
6. **权限与租户**（3.7）：确认网关职责，明确 data-table 的信任边界，收紧 CORS。
7. **测试套件化**（3.9）：去除隐式环境依赖，脚本转为可进 CI 的测试。

## 6. 可以开始试点的条件

- 数据仅限内部可信用户，且网关已承担认证。
- 单数据集行数在可人工核对的范围内，并接受结果需人工复核。
- 同一数据集不混用不同向量化策略切换。
- 不对外承诺检索质量，直到完成 3.8 的基线。
- 不向生产库写入未经验证的存量数据集（索引身份问题未解决）。

### 验证

- 单测：`bun test --isolate` 下 data-table、providers、vector.service 共 89 个通过，其中新增 7 个写入一致性用例（补偿、先写后清、建库冲突）。

### 已知但未处理的问题（如实记录）

- 全量单测（`bun test --isolate`，1396 条）中有 7 个失败与本次改动无关：2 条是 AGENTS.md 已登记的 graph 缺陷探针（minScore 语义反转、rerank 置信度）；4 条为 Wiki HTTP e2e，只因 bun 自动加载的 `.env` 设置了 `KNOWLEDGE_DATABASE_URL` 而运行，未验证其根因；1 条为审计探针（已改为回归，见上）。
- 写入失败前的旧行为未在原代码上做对照实验（未 stash 当前未提交改动）。"修复前会失败"的结论来自代码路径的静态核对：原 `insertRowsFromMetadataBatch` 在 COMMIT 之后才调用 embedding；原 `revectorizeRowsBatch` 在 embedding 之前执行 `deleteByRowId`。
- 未做：storageId 迁移存量索引（F01 完整修复）、异步索引任务表与租约（F02 完整修复）、行级聚合 F07、类型化列、认证与租户、质量评估基线。这些需要产品层决策或较大改动，不在"不破坏核心逻辑"的范围内。
