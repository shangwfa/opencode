# data-table 优化方案：基于当前实现的最佳实践落地

日期：2026-10-14。本文件是设计与实施建议，**不代表已实现**。本轮只更新方案文档，没有修改业务代码。

前置依据：[源码深度审核](./implementation-review-2026-10-14.md)、[同类产品官方资料](./industry-comparison-2026-10-14.md)。

## 1. 总体决策

保留 Hono、PostgreSQL、pgvector、pg_trgm、每数据集动态输出表，以及 RAG 底层检索能力。当前不引入 Elasticsearch、Typesense、Redis、Kafka 或新的 Agent 框架。

优化核心是让 data-table 有自己的**字段模型、记录身份、索引任务、检索计划和结果契约**，而不是继续把表格包装成文档 RAG。

| 当前 | 推荐目标 | 理由 |
|---|---|---|
| rows + columns 的同步 JSON 接口 | 保留；额外增加来源适配与导入任务 | 不破坏已有调用方 |
| 值 String() 后 join('') | 字段策略驱动的确定性序列化 | 保留边界、标签和类型语义 |
| 全行无差别向量化 | 短记录带标签行向量；长字段按字段分块 | 避免不必要的单元格向量成本 |
| 请求里先写行，再调用 embedding | PG 行 + 持久化任务；事务外构建，事务内版本发布 | 失败可恢复，多 pod 可接管 |
| 多阶段分支优先于 searchType | 先按 searchType 分派，再处理本路召回 | 保证检索行为名实相符 |
| SQL 前 200 行 + 全库召回交集 | 受条件约束的精确／ANN 检索计划 | 避免确定性漏召回 |
| chunk topK | 新记录模式按 rowId 聚合后取 topK | 用户搜索单位是业务记录 |

不选择一次性重写：先处理已有数据的正确性，再引入新能力。

### 多策略支持原则（按用户确认更新）

**下面列出的策略都应纳入目标能力，而不是选一种后删除其他策略。** 实施仍分批，但最终通过统一的配置和检索计划支持不同场景。

策略分两层：索引配置属于数据集／索引版本；查询配置属于单次请求。不要用一个 mode 同时决定所有行为。

| 维度 | 目标策略 | 配置位置 | 是否通常需要重建 |
|---|---|---|---|
| 向量组织 | row（选定字段合成行向量）、field（字段独立向量／分块）、group（多个字段组成语义组）、row+field（同时建立行和字段索引） | 数据集索引配置 | 是 |
| 分块 | none、按长度／递归、适合指定字段格式的策略 | 字段／语义组配置 | 是 |
| 检索类型 | semantic、keyword、hybrid | 查询请求 | 否，需对应索引已就绪 |
| 检索范围 | 全部授权可检索字段、指定字段、指定语义组 | 查询请求 | 否，但不能查询不存在的索引 |
| 多路融合 | RRF、加权 RRF、分数加权（分数具备可比语义时） | 查询请求 | 否 |
| 召回执行 | exact、ANN、auto（按候选规模和预算选） | 查询请求与数据集默认值 | ANN 需预先建立索引 |
| 字段权重 | 检索侧字段 boost，默认全 1 | 查询请求或数据集默认 | 否（不改索引） |
| 查询增强 | 不增强、多阶段、HyDE、多查询及其已验证组合 | 查询请求 | 否，需明确适用检索类型 |
| 结果单位 | row、chunk／evidence | 查询请求 | 否 |
| 返回字段 | 全部授权返回字段、selectFields 投影 | 查询请求 | 否 |
| 索引执行 | 同步等待、异步任务 | 写入／导入请求 | 否，底层共用持久化任务 |

这不是承诺参数之间任意笛卡尔组合都有效。每个执行计划先校验支持矩阵：

- field/group 范围检索必须有对应索引。只有混合 row 向量时，不能假装能在某个字段独立做语义召回。
- row+field 启用后，同时检索时按 rowId 聚合各路结果；不能重复计票让向量较多的行天然占优。
- hybrid 明确执行词法与语义两路；纯 keyword 不偷偷启用 embedding 或 HyDE。
- 不同模型／维度的向量路分开检索，再融合排名；不能直接混写到同一固定维度列。
- 分数加权要求各路分数可比较；没有校准时优先排名融合，不把 RRF 排名分当语义相似度。
- ANN 不可用时，仅在请求允许降级且预算足够时切换 exact，并报告原因；否则显式返回能力／依赖错误。
- 配置变更需要重建时，新版本完成再切换。请求不能临时改变模型、序列化或分块参数而仍查询旧索引。

默认策略只是便捷预设，不限制能力。建议新数据集使用 row 预设；明确字段搜索需求的数据集选择 field/group；确需两者才启用 row+field，并显示预计向量数量与成本。

### 字段权重决策（2026-10-14 实验后结论）

**有必要，但形态是检索侧行级聚合时的字段 boost（默认全 1），且应与 F07 行级聚合同批落地，不单独提前做。**

实验依据（OpenRouter 真实向量，临时探针 `field-weight-probe.ts`，取 v2 实测的两个排序失误案例）：

| 案例 | 字段分数分布 | 加权能否纠正 |
|---|---|---|
| S4 "用户怎么登录系统"（期望创建会话，实际 top1 创建用户） | 期望行 description=0.5241 为全场最高；实际 top1 靠 summary=0.4656 | 无需权重：max 行级聚合在所有权重下都选对；加权平均仅在 summary^0.5 时也对 |
| S2 "读一下表格文件"（期望读取Excel，实际 top1 提取表格数据） | "表格"字面在提取表格数据 name=0.6005 领先 0.055；desc 两行几乎平手 | 权重无解：name^1/^2/^0.5 与 max/加权平均组合均翻转不了，属语义歧义（"表格文件"两义），embedding 判断不算错 |

结论：
1. 已观测的两个排序失误中，一个靠 field 策略 + 行级聚合（max）即可纠正，无需权重；另一个是语义歧义，权重救不了。字段权重的收益尚未在我们数据上成立。
2. 向量级结果上没有权重的正确作用点，必须先有行级聚合（F07），字段权重才有意义（作为聚合时各字段分数的组合系数）。F07 落地时同步引入，默认全 1 不改变现状。
3. 若将来启用，设计要点：检索侧参数（索引时无法对向量预加权，重复文本会破坏语义）；对外分数保留原生相似度或显式标记 scaled（吸取 RRF 排名分外泄的教训）；keyword 路径同步支持 boost；任何非默认权重集需先用 L2 评估基线证明优于全 1，不拍脑袋调参。

接口与状态需区分三份信息：configured（数据集建立了什么索引）、requested（本次请求什么策略）、effective（实际执行什么策略）。记录候选数、各路耗时、融合、重排和降级，方便解释结果和审计执行过程。

验收按“各策略独立用例 + 合法组合 + 非法组合拒绝”组织。数据集默认值与请求覆盖、版本重建、成本上限同样要测；不能只测默认 row+semantic 后宣称多策略支持完成。

## 2. 第一阶段：修正确性，不扩大产品范围

### 2.1 修检索编排

修改 `src/data-table/services/database-rows-search.ts`。

- semantic：执行向量检索；多阶段、HyDE、多查询仅在本路内编排。
- keyword：执行词法检索；queryExpansion 要么明确支持词法扩展，要么拒绝，不得偷偷切成语义检索。
- hybrid：明确执行语义和词法两路，再融合，最后可重排。
- 权重默认值使用 `??`，允许权重为 0；全部权重为 0 则拒绝或明确约定，不能隐式修正。
- 响应／日志记录 effectiveSearchType、召回路数、fusionMethod、有效候选数。
- 检索失败和无结果分开；降级必须显式说明，不能把依赖错误伪装成空结果。
- 区分原生相似度、融合排名分和重排分；不要直接对未经校准的 RRF 分使用语义 minScore。

兼容：保留旧字段 searchType、items 和显式 keyword×多阶段的校验。新增执行信息，不改变字段含义。

### 2.2 安全地分配索引身份

修改 `services/database.service.ts` 与 `db/schema.ts` / `db/index.ts`。

- 公共 datasetId 可以继续兼容原值；新增不可变、服务端生成的 storageId。
- 动态表和向量表按领域前缀 + storageId 命名，不从用户名称或 `kb_` 前缀推导。
- 向量物理表名在 data-table 注册表内唯一；新命名与文档 RAG 空间隔离。
- 所有访问经注册表解析，避免某些路径读取 indexName、另一些路径重新计算。
- 迁移前先检查 data-table 内部以及与 RAG 注册表的物理名称重复。发现共享索引先隔离／重建，不能直接 DROP 旧表。
- 缓存以 storageId / indexVersion 为键，切换时使旧缓存失效；不能依赖单 pod 内存缓存作为事实源。

### 2.3 纠正测试可信度

修改现有用例及新增目标回归测试。

- DT25 必须证明全文、向量两路都执行，且 fusion 参数生效。
- DT33 直接验证 `len(items) <= topK`，不能先用 min() 截断断言值。
- DT06 检查调用／索引内容 hash，不能只看向量数量。
- 禁止两个空值相等被算 PASS；HTTP、JSON、PG 错误必须保留。
- 服务不可达与模型失败是环境阻塞；业务接口异常不能一律记 SKIP。
- 响应文件改为本轮唯一目录；清理仅限本轮记录的 datasetId。

审计探针刻画不良行为。修复后应转成目标契约测试，不能继续以“问题仍存在”为 PASS 来做上线门禁。

**阶段验收：**三类型执行正确、0 权重生效、物理索引无别名共享，历史正常路径不回退。该阶段不能宣称过滤与失败恢复已完成。

## 3. 第二阶段：记录与索引可靠一致

### 3.1 最小持久化模型

仍使用现有 PG，不引入额外队列系统。

- dataset：storageId、schemaVersion、activeIndexVersion、目标模型／维度／策略配置、生命周期状态。
- record：稳定 rowId、可选 sourceKey、rowVersion、indexState、indexedVersion、索引内容 hash。
- index job：datasetId、rowId 或重建批次、目标 rowVersion / indexVersion、状态、attempts、nextRunAt、leaseUntil、leaseToken、lastError。

字段名称是建议。表与索引设计应与当前 Drizzle 业务表约定一致；原始来源、任务和权限身份需从真实接入契约确定，不凭空引入固定 tenant 字段规则。

### 3.2 写入与更新协议

修改 `database.service.ts`，增加本域 `services/index-job.service.ts`。调整底层 `PgVectorStore`，提供受控的调用方事务写入能力。

1. 校验并规范化记录。
2. 在同一 PG 事务写行、递增 rowVersion、写对应索引任务。
3. 提交事务。worker 领取任务并读取准确版本的索引输入。
4. 在 PG 事务外分块和调用 embedding。
5. 开启短 PG 事务，锁定记录与任务，校验 rowVersion、目标 indexVersion 和 leaseToken。
6. 版本仍有效则写入新向量、清理旧版本、更新 indexedVersion 与任务终态，原子提交。
7. 版本已过时则丢弃结果或安排当前版本任务，不允许覆盖新版本。

worker 采用 `FOR UPDATE SKIP LOCKED` 短事务领取，提交后执行模型调用；lease 续期及 fencing 防止过期 worker 发布。禁止持有 PG 行锁等待模型。

**注意：**现有 VectorService / PgVectorStore 使用自己的 pool。仅让它们共享 Pool 并不意味着同一事务；原子发布必须使用同一个 PoolClient，底层不得私自 BEGIN / COMMIT。

任务按版本幂等，指数退避重试，超过上限记录可恢复失败。后台扫描过期租约与漏索引记录。进程重启不丢任务，多 pod 无主节点也能执行。

### 3.3 搜索一致性选择

默认建议只返回 `indexedVersion == rowVersion` 的记录。更新尚未完成时标记 pending，不能把旧命中文本与新行内容混合返回。

旧向量在新向量发布前保留，便于安全重试；**保留旧向量不等于可以用它命中后回填当前行**。如果产品要求更新期间仍可搜索旧快照，需要额外保存旧行快照与版本关联，不在首版默认引入。

### 3.4 删除协议

单条／批量删除先在事务中校验、标记不可见并写清理任务；检索排除删除记录。物理清理可幂等重试，不吞异常后假定成功。

批量存在性要求和部分成功要求只能选一个明确契约。兼容现有批量更新语义时，推荐批量校验后整体提交；若保留部分成功，返回每项状态而非仅整体 404。

### 3.5 API 兼容

不要把现有成功 200 悄悄改成“仅已排队”。

- 旧同步模式：也先创建持久化任务，再等待同一任务索引完成；完成后返回原成功结构。
- 超时／失败：明确返回 operationId、已接收的 rowId 与索引状态，避免调用方盲目重建重复记录。具体 HTTP 契约需同步客户端评审。
- 新异步模式：调用方显式选择，返回 202 + jobId；提供任务状态和重试接口。
- 导入 upsert：sourceKey 在数据集内唯一，重导使用稳定 key，不每次生成全新 rowId。

**阶段验收：**embedding 故障、部分批次失败、pod 强杀、租约竞争、并发更新、更新后立即删除，都能按约定恢复且不发布旧版本。

## 4. 第三阶段：字段建模与检索契约

### 4.1 字段配置，而非全部字段一视同仁

扩展 `types/database.types.ts` 与 registry 的 columnDefinitions。

| 属性 | 用途 | 兼容方式 |
|---|---|---|
| key / name | 内部安全列名 | 旧 name 可作为 key |
| displayName / sourcePath | 中文表头、来源字段或嵌套 JSON 路径 | 可选，不修改旧字段名 |
| type | string、number／decimal、boolean、datetime、json 等 | 旧数据保持 legacy text，禁止猜测强制转换 |
| searchable / semantic / filterable | 字段的词法、语义和过滤角色 | 旧配置经显式 legacy 策略兼容 |
| weight / semanticGroup | 查询权重与 embedding 分组 | 没有需求时不启用复杂分组 |
| returnable / sensitive | 输出策略与脱敏提示 | 不替代真正的字段授权 |

数值金额优先精确 decimal；日期规定时区；Excel 数值或字符串编码应保留来源含义。原始记录可保存 JSONB；类型化投影仍落当前动态表。原始 JSON 保留的数据自身也需要权限与保留期约束。

### 4.2 确定性索引文本

将 `embeddingTextFromRecord` 收敛为本域 `services/record-indexing.ts` 的纯逻辑，负责字段选择、序列化、分组及内容 hash。业务任务调度不放进 utils。

- 行级短文本使用字段标签、分隔符与固定顺序。
- 嵌套对象明确规范化，不允许 `[object Object]`。
- 长自然语言字段按字段单独分块，保留 fieldId。
- SKU、金额、日期、租户、权限不默认向量化。
- 只有参与索引的字段或策略变化才触发重建。
- 不参与语义索引的字段也可用于词法索引，不依赖 embedding 成功才有关键词能力。

现有 keyword 从向量表 metadata.text 读取，因此不能自动实现“embedding 挂了仍能完整关键词搜索”。需改为来自记录的确定性词法内容／投影，或独立持久化词法索引内容。

### 4.3 条件过滤与排序

新增字段类型驱动的 filter AST 与编译器；同时为旧字符串子串 filter 保留兼容解析。

新语义明确支持 eq、in、范围、null、and/or 等已验收子集；字符串精确与 contains 分开，不能让用户以为所有 filter 都是精确等值。

生成参数化 SQL、校验字段与权限。条件约束在检索 SQL 内执行，不能先取任意 200 行再求交集。

- 小过滤集合：精确距离排序，完整检查 topK。
- 大集合：ANN + 过滤 + 迭代扫描／预算与召回评估。
- 严格正确性场景：提供精确模式；不能承诺 ANN 永远不漏。

pgvector 版本和实际查询计划要核实。即使 SQL 中有 WHERE，ANN 也可能过滤后结果不足；仅添加 join 不保证迭代扫描有效。必须用 `EXPLAIN (ANALYZE, BUFFERS)` 和精确基线验证。

查询最好使用可索引的距离排序形态，再在结果层计算对外 score；具体是否使用 ANN 以查询计划为依据。

### 4.4 行级结果与输出保护

先检索证据候选，再按 rowId 聚合评分／融合，最后截断记录 topK。分块密集行不能挤掉全部其他记录。可选 row 级重排时构造授权字段上下文。

保留旧 chunk 返回模式，新客户端显式选择 `resultMode=row`；记录模式成熟后再评估变更默认。返回 matches（field、text、chunk）、row、score 与有效检索信息。

selectFields、授权与脱敏分别处理，并统一约束 row、metadata、text。受限字段若参与 embedding 也可能产生推断泄露；不能只在最后删除键。敏感数据默认不进入公共语义索引，复杂字段授权按独立检索范围设计。

外部 `/vectors` 通道应声明为自带向量／管理模式；不能允许任意无所属行向量混入自动维护的记录索引，否则聚合、删除与权限都失去可靠关联。

**阶段验收：**中文列、嵌套 JSON、精确 SKU、价格日期范围、字段限制、长字段聚合、敏感字段与无相关结果均满足定义好的契约。

## 5. 第四阶段：多来源导入与质量／规模验收

来源适配器只负责读取与解析，统一产出字段、原始记录、sourceKey 和来源定位。复用记录写入及持久化索引任务，不各自实现一套向量化。

- JSON：对象数组、嵌套路径、类型冲突与空值。
- CSV：编码、BOM、分隔符、转义、字段内换行；保留前导零 ID。
- Excel：sheet 选择、表头、日期／数字格式；明确公式取缓存值或拒绝，不自行执行宏／公式。
- 数据库：只读凭据、参数化查询、分页／游标、主键；只有承诺持续同步时才加入增量与删除检测。

校验请求／文件大小、字段数、记录数与处理预算；流式或批次解析，逐项记录错误。不要一次性在内存收集整个文件和所有 chunkTasks。

先做一次性导入，验证用户价值后再增加持续同步。不要第一版同时引入 CDC、全连接器管理和自动 schema 演进。

真实评测必须包括：

- 超过 200 条过滤命中，全库高分却范围外的干扰记录。
- 同义表达／口语改写与精确编号查询；无相关结果。
- 一行长文本生成多个 chunk，检查不同记录数量。
- repeated import／并发更新／源删除与故障恢复。
- 数据量、导入吞吐、P95 查询延迟、任务队列积压和收敛时间。

性能优化顺序：输入背压 → 查询计划 → 批量向量写入 → 连接池与索引 → 重排成本。不要先扩大所有 recallTopK 或为所有字段建索引。

指标为 Recall@K、nDCG@K、越界结果数、无关误命中率、不同记录数。质量阈值和容量必须根据代表数据集与业务 SLO 确定，不给无依据的固定承诺。

## 6. 改动落点与复用边界

| 位置 | 优化责任 |
|---|---|
| `data-table/types/database.types.ts` | 字段、索引策略、filter 和结果契约 |
| `data-table/db/schema.ts` / `db/index.ts` | registry、任务与记录状态迁移，幂等初始化 |
| `data-table/services/database.service.ts` | 数据集与行生命周期，事务创建任务 |
| `data-table/services/record-indexing.ts`（拟新增） | 索引输入序列化、字段分组与 hash |
| `data-table/services/index-job.service.ts`（拟新增） | PG 任务领取、租约、重试与版本发布 |
| `data-table/services/database-rows-search.ts` | 领域检索计划、条件、融合与行结果 |
| `data-table` 来源适配模块（后续） | 文件／数据库转统一记录批次 |
| `rag/knowledge-base/vector/vector-store.ts` | 通用 PG 向量原语及调用方事务能力 |
| `rag/knowledge-base` 通用词法／融合服务 | 可复用算法，不拥有 data-table 导入和记录状态 |

共享能力通过 facade 暴露；不让其他域直接依赖 data-table 内部表。新增环境配置统一进入 `config/env.ts`，不沿用业务代码随处读取环境变量的模式。

schema 与默认模型配置变更需要迁移流程，不能用现有 CREATE TABLE IF NOT EXISTS 当作完整 schema 升级。初始化取消隐式 import 时重复启动的副作用时，需回归启动与多 pod 并发迁移。

## 7. 存量迁移与回退

1. 只加字段／任务表，保留旧 API 与原始数据，不直接强转所有 TEXT 列。
2. 扫描物理名称碰撞、孤儿向量、行索引缺失与模型维度不一致，输出报告。
3. 新 storageId、新索引版本在后台构建；旧索引暂不删除。
4. 按数据集影子查询，对比结果、权限和延迟。影子失败不污染旧检索。
5. PG 事务切换 activeIndexVersion；所有 pod 按新版本解析，避免缓存指向旧表。
6. 观察稳定后再清理旧索引；发生故障可回切已验证的兼容版本。

如果旧索引存在跨库污染，不应把回退到旧索引称为安全回退，需隔离后重建。回退语义依数据版本兼容性判断，不是简单切一个开关。

## 8. 建议首先执行的工作单

**第一批只做：检索三类型编排、零权重、有效检索信息、严格测试断言，以及物理名称碰撞扫描／新索引身份设计。**

先沉淀目标失败用例，再修复，实现后执行单测及 Docker HTTP + PG e2e。凡涉及 SaaS 会话执行，需要订阅会话 SSE 并记录过程；知识服务独立 API 验收不虚构不存在的会话 SSE。

第二批做持久化任务和版本发布；第三批做字段与过滤／行结果；第四批补来源适配并进行真实模型与容量验收。

这一路径保留当前投资，同时优先解决会导致结果错误、数据不一致和隔离失效的问题。不要先用大量导入接口把当前不可靠的索引流程扩展到更大规模。
