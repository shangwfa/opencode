## 2. 产品目标对照

产品目标：用户上传 JSON / CSV / Excel / 数据库数据 → 创建输出表 → 按策略向量化 → 提供语义、关键词、混合检索。

| 能力 | 接口覆盖 | 缺口 | 严重度 |
|---|---|---|---|
| 文件导入（CSV/Excel/JSON） | 无 | 没有上传接口、解析任务、字段映射、导入进度与错误报告 | **阻断** |
| 数据库导入 | 无 | 没有数据源注册、只读查询、分页/游标、增量同步 | **阻断**（若需求包含） |
| 幂等导入（重复导入不产生重复行） | 无 | `POST /rows` 只能追加，生成新 rowId；没有 sourceKey 或 upsert | **阻断** |
| 导入任务状态 | 无 | 同步返回，失败只能看 HTTP 错误；没有任务 id | 高 |
| 索引状态与健康度 | 无 | 看不到哪些行待索引、已索引版本、策略是否生效 | 高 |
| 手动重建索引 | 无 | 只能通过 PATCH 间接触发，无法单独重建或修复 | 高 |
| 语义检索 | 有（POST） | — | 完整 |
| 关键词检索 | 有（POST） | GET 版不支持 | 中 |
| 混合检索 | 有（POST） | GET 版不支持，且无混合权重参数 | 中 |
| 字段限定检索 | 有（POST） | GET 版不支持 | 中 |

## 3. 具体问题

### 3.1 GET 检索（`GET /:id/query`）功能残缺

源码（`routes/rows-search.ts`）：GET 只读取 `page`、`pageSize`、`query` 三个参数，构造的请求体也只有这三项。因此 GET 不能：

- 指定 `searchType`（只能走默认语义）；
- 使用 `filter` 或组合检索；
- 使用 `searchFields`、混合权重、`fusionMethod`；
- 分页（`page`、`pageSize` 不在检索 schema 中，被忽略）。

建议：要么删除 GET 版，要么让它接受与 POST 相同的参数（query string 解析为同一 schema）。当前状态会让调用方误以为 GET 与 POST 等价。

### 3.2 检索没有真正的分页

`RowsSearchRequestSchema` 没有 `page` 字段。调用方只能用 `topK`（上限 200）截取结果，无法翻页取全部匹配。对"搜索指令库""搜索接口"这类场景，结果超过 200 条时无法获取完整结果。

### 3.3 写入不幂等

`POST /:id/rows` 每次生成新 rowId（`r_<ts>_<i>_<rand>`）。同一份数据重复导入会产生重复行与重复向量。没有 `sourceKey`，无法实现"按来源主键 upsert"，也无法做增量同步或删除同步。这是导入功能的前提缺口。

### 3.4 向量接口暴露了内部实现

`/vectors` 与 `/vectors/query` 绕过行模型直接写入向量，与行的 `rowId` 关联、删除、聚合、字段限定都可能失效（例如手写向量没有 `rowId`，删行时无法清理）。这两个接口应限制为管理员接口，或在文档中明确"不参与行级语义"。

### 3.5 错误映射不一致

POST 写行对不存在的数据集返回 400，其它行接口返回 404（已记录在 rows 用例中）。接口对调用方的错误语义不统一。

## 4. 建议的接口补充（按优先级）

**P0（支撑产品目标的前提）**

1. `POST /:id/import`：统一导入入口，支持 `format: json | csv | xlsx`，返回 `jobId`。文件通过 multipart 上传或 `contentBase64`。解析在服务端完成，输出标准行批次。
2. `GET /:id/import/:jobId`：任务状态、进度、行级错误（行号、原因）。
3. 行 upsert：`POST /:id/rows` 增加可选 `keyColumn` 或 `sourceKey`，相同 key 更新而非追加；或新增 `PUT /:id/rows`。
4. `GET /:id/index`：索引状态（策略、模型、索引版本、已索引行数、待索引行数、失败行数）。
5. `POST /:id/index/rebuild`：手动重建，返回任务 id。

**P1（完善检索能力）**

6. GET 检索与 POST 参数统一（或删除 GET 版）。
7. 检索增加 `page`/`offset` 与 `total`；或明确只返回 topK 并在文档中说明上限。
8. 行级结果模式：`resultMode=row`，按 rowId 聚合（即 F07）。
9. `GET /:id/rows` 增加 `q` 关键词参数。

**P2（运维与完整性）**

10. `GET /:id/export?format=csv|json`：导出当前数据。
11. `DELETE /:id/rows` 支持 `filter` 条件删除（需要二次确认参数，防误删）。
12. 字段元数据：列类型、是否可检索、是否语义索引。配合列类型 schema（第 2 节 CSV 场景）。
13. `/vectors` 两个接口标记为管理员接口，或移出公共路由。

**横向（所有接口）**

14. 认证与租户：在路由层增加中间件，数据集归属租户；当前未验证网关是否承担该职责。
15. 统一错误码：404 资源不存在、409 冲突、400 参数错误、422 语义错误（如"该策略不支持该参数"），与已有的 INDEX_NAME_CONFLICT → 409 保持一致。

## 5. 结论

**接口对"数据集与行的增删改查 + 三种检索"是完整的；对"数据导入与运维"不完整，对产品目标（多来源导入）是不完备的。**

最关键的缺口是：没有导入接口、没有幂等写入、没有索引状态。这三项缺失时，即使检索能力再好，也无法支撑"用户上传文件并持续使用"的场景。

建议先补 P0 的第 1、3、4 项，GET 检索（第 6 项）作为小修可以同批完成。
