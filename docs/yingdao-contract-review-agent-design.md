# 影刀合同预审 Agent 提示词重构说明

> 对象：BOSS 审批流程「AI 审批节点」中定义影刀销售合同预审 Agent 的系统提示词（下称"原稿"）。
> 产出：[prompt.md](./yingdao-contract-review-prompt.md)（v3，可直接粘贴）。
> 定位：**语义等价重构**——不改变任何一条法务规则，只改组织方式。除下文标为"行为修正"的 3 处外，判定结果与 v2 一致。

---

## 一、诊断：乱在哪

乱不是"写得不够详细"，而是**三种不同性质的内容被压在同一层**：

| 内容性质 | 量级 | 应有的约束方式 | 原稿现状 |
|---|---|---|---|
| 编排（分流、幂等、上传、评论顺序） | ≈40% | 代码/工具链强制 | 写成自然语言，靠模型自觉 |
| 判定规则（三类驳回、模板、法务口径） | ≈35% | 版本化规则集，法务可改 | 与流程、格式混排 |
| 写作规范（报告三章、评论模板） | ≈25% | 独立的格式契约 | 分散在 5 个章节 |

模型读到的是一张平面清单，无法区分"硬约束"和"背景说明"，于是作者不断加"最高优先级"去压——这就是失控的机制。

### 1.1 六个具体病症（均有原文依据）

**① 有两个"最高优先级"，互相打架。**
章节「审批结论判定（最高优先级）」与章节「最高优先级原则」平级并列。两条规则真正冲突时，模型无解，只能随机挑一个——而这种冲突恰恰最容易出现在边界案例上。这是最严重的结构冲突。

**② 同一规则重复 3–5 次，措辞还不完全一致 → 必然漂移。**

| 规则 | 出现位置 | 次数 |
|---|---|---|
| 分流三步（操作类型 → 格式 → 标题） | 核心任务#1、执行顺序#2–3、附件分流整章、附件分流·四、最高优先级#2 | 5 |
| 只有三类可驳回 | 核心任务#2、核心任务#5、审批结论判定、最高优先级#3、评论格式 | 5 |
| 失败即停 | 执行顺序#12、最高优先级#1/#8/#9、最终返回 | 3 |
| 报告唯一、不得第二份 PDF | 核心任务#4、执行顺序#6 | 2 |
| 「不得据此驳回」的负面列举 | 审批结论判定末段、最高优先级#5、附件分流·二.3、最高优先级#2 | 4 |

改一条规则要同步 5 个地方，漏一处就产生行为矛盾，且**没有任何机制能发现漏了**。

**③ 靠负面清单兜底，永远列不完。**
原稿散落着至少 16 处"不得据此驳回"：非我方模板、模板修改、税率、付款顺序、账期、服务保障、知识产权、违约责任、合同终止、不可抗力、管辖、适用法律、生效约定、合同份数、旧版模板、格式不符。每遇到一次误驳回就补一句，清单只会变长。
正确的写法只有一句：**驳回集合是封闭的 = {B1, B2, B3}，其余一律进报告。** 这一句替代了 16 处列举。

**④ 实现细节侵入提示词，占了约 1/4 篇幅。**
幂等键 `legal-risk-report-{taskId}-v1`、`uploadMethod` / `ossUploadUrl` / `requiredHeaders` 原样回传、`%PDF-` 前缀、`file_size` 一致、`attachments_json` 精确形状、`instance_code`、重试一次……这些全是确定性操作，用提示词约束等于祈祷。
每一条都是一个**静默失败面**：模型不会报错，它只会把幂等键写错一位，然后系统里多一份报告。

**⑤ 规则没有 ID，但带日期，说明它会变却没版本机制。**
「以 2026-10-13 法务确认的最新基础审核规则为准」「知识库中的旧规则不得……」——这明显是规则迭代留下的补丁。可全文没有任何规则编号，法务说"第三条改一下"时无法定位，也**无法为单条规则挂回归用例**。

**⑥ 输出契约自相矛盾。**
「最终返回」写"只能按实际分支返回以下**两种**格式之一"，紧接着给了第三种失败格式；默认通过分支的评论文案（`基础审核结论：通过。备注：…`）与「评论格式」的通过模板（`基础审核结论：通过（未命中基础审核驳回条件）。`）并存，未说明谁优先。

### 1.2 另外两个隐性问题

**⑦ 缺少输入字段契约。** 全文只有"从触发消息中取得 taskId"这一句，没有字段表，没有 `form` 结构示例。而分流逻辑高度依赖 `form.附件` 的真实形状（JSON 字符串？Markdown 链接？操作类型在哪一层？）——**这是最容易出错的地方，却写得最少。**

**⑧ 「证据」只出现一次，没有落地。**
「只有证据确认命中以下任一类条件时」是全文最关键的一句约束，但没有任何地方要求模型**输出**证据。没有证据字段，就无法复核"这次驳回是不是编的"，评论里的"具体原因"也只能靠自由发挥。

### 1.3 两个补丁其实在防同一件事

「最高优先级#5 旧版模板有效」+「风险报告格式#4 不得把未变更的标准条款改写成谈判建议」，看着无关，实则指向同一件事：**要不要把旧版模板、未变更的标准条款算作缺陷**。
应该合并成一条正向原则：**审查基准 = 本单实际使用的模板，不是最新模板。** 一句话覆盖两条补丁。

## 二、重构做了什么

### 2.1 分五块，每块只放一种东西

```
§0 边界      身份 / 输入字段表 / 输出     —— 不再重复
§1 管线      S1→S8，每步一张表            —— 只讲顺序，不讲规则
§2 判定      B1/B2/B3 + 证据门槛          —— 规则集，带 ID，可版本化
§3-4 产出    评论模板 / 报告契约          —— 格式契约，与判定解耦
§5-7 失败·安全·输出                       —— 失败语义 + 抗注入 + 单一 JSON
```

硬约束用 `[硬]` 标记，判定用 `[判]`，停止用 `[停]`，全文统一。

### 2.2 关键动作

| 动作 | 效果 |
|---|---|
| 删掉"最高优先级"两级结构，规则按"驳回/报告"二分 | 消除无解冲突 |
| 驳回集合写成封闭式 `{B1,B2,B3}` | 替代 16 处负面列举，新增场景默认进报告 |
| 每条规则给 ID（B1/B2/B3、S1–S8、阶段码） | 可被法务、用例、PR 直接引用 |
| 引入**证据门槛**：命中必须给 `{规则, 角色, 条款序号, 原文}` | 防幻觉；评论的"具体原因"有来源 |
| 阶段码 `S2c_标题解析` 等 | 失败可定位、可统计，不再只有一句"失败" |
| 输出合并为单一 JSON，用 `审核模式` 区分 | 修掉"两种格式"的矛盾；**字段名保持不变**，下游解析不受影响 |
| 报告只留"写什么"，"怎么排"全部交给 skill 的 report-format.md | 消除第二处 18 项清单，避免两处漂移 |
| 输入补成字段表 | 分流失败的高发区有了明确契约 |

### 2.3 行为修正（3 处，均为原稿自相矛盾处，非规则变更）

1. **默认通过分支的评论文案以「S2 出口 · B」为准**，不再套用「评论格式」的通过模板——原稿两处并存且未说明。
2. **失败返回单列**，不占用"两种格式之一"。字段与原稿完全一致。
3. **"18 项清单"只留在 skill 的 `references/report-format.md`**，提示词里明确"不复制"。原稿其实已经这么做了，只是没说清，容易被后人复制进提示词造成两处漂移。

### 2.4 原文 → v3 对照（可逐条核验）

| 原稿章节 | v3 位置 | 处理 |
|---|---|---|
| 角色与核心任务（6 条） | §0、§1、§S2 出口 | 拆入边界与管线，删除与其他章节的重复 |
| 必须遵守的执行顺序（12 步） | §1 的 S1–S8、§4.5、§4.6 | 12 步归并为 8 阶段；纯机械步骤集中到 §4.6 表 |
| 附件分流（一–四） | §1 S2a / S2b / S2c + S2 出口 | 规则原样保留，补"逐份记录"字段与出口二分支 |
| 审批结论判定 | §2.0–§2.4 | 16 处负面列举 → 封闭集合；规则表格化并编号 B1/B2/B3 |
| 风险报告格式（1–5） | §4.1–§4.6 | 三章结构不变；18 项显式委托 skill；新增提交序列表 |
| 评论格式 | §3 | 原样保留，补默认通过分支的归属 |
| 最高优先级原则（9 条） | §0、§2.0、§4.4、§6 | 拆散归位，"最高优先级"层级整体删除 |
| 最终返回 | §7 | 三种格式合一，**字段名不变** |

## 三、应该搬出提示词的（这才是根因）

原稿 40% 的内容不是"规则"，而是"流程"。流程用自然语言写，就必然要写重、写长、写矛盾，而且**改一次错一次**。

| 原稿条目 | 失败时的表现 | 应由谁保证 |
|---|---|---|
| 幂等键 `legal-risk-report-{taskId}-v1` | 写错一位 → 同一审批生成两份报告 | 编排层生成，不暴露给模型 |
| `uploadMethod` / `ossUploadUrl` / `requiredHeaders` 严格回传 | 删改 header → 上传 403 | 上传 SDK |
| `%PDF-` 前缀 + `file_size` 一致 | 模型"看着像 PDF"就放行 | 校验函数，失败直接抛 |
| `attachments_json` 精确为 `[{"fileKey":…}]` | 多一个字段 → 评论接口 400 | 序列化层 |
| `instance_code` = 当前 `instanceCode` | 串号 → 评论写到别人单子 | 函数入参，不靠模型拼 |
| 网络错误重试一次 | 模型无状态，无法保证"只重试一次" | 重试中间件 |
| S2a/S2b（操作类型过滤、扩展名过滤） | 纯确定性规则，模型做只会引入漂移 | 代码 |
| 评论成功后才审批 | 步骤顺序错误 → 审批过了但没留痕 | 事务/状态机 |

搬完之后，模型只需要回答四个问题：**标题里有没有合同/协议、18 项内容是什么、命中 B1/B2/B3 吗、评论怎么写。** 提示词能降到 150 行以内。

### 3.1 一个诚实的取舍

v3 约 **350 行、4100 个汉字**，篇幅与原文基本持平（表格占行更多）。缩短不发生在这一次——这一次买到的是：

- 规则从"散落 20 处"变成"3 处单一来源"，改规则不再漏改；
- 每条规则可被 ID 引用，可挂用例、可定位失败；
- 判定范围从"负面列举"变成"封闭集合"，新增场景默认不驳回。

**真正的缩短发生在 P1**：把上表 8 项搬进代码后，§0.1、§4.5、§4.6、§5 大半会消失。

## 四、迁移路线

**P0（只改提示词，本周可上）**
用 `prompt.md` 替换原稿。字段名与分支语义不变，下游解析零改动。先观察驳回率、阶段码分布。

**P1（编排层）**
把 S2a/S2b、幂等、上传校验、评论→审批的原子性搬进代码；模型输入从"一堆下载链接"改为"已分流的待审合同 + 每份的本地文本/结构化内容"。此时提示词只剩 §2–§4。

**P2（规则工程）**
规则抽成 `rules.yaml`（ID、生效日、条件、证据要求），提示词按 ID 引用；建立黄金用例集（历史 20–30 单，含 3 类驳回与各类误驳回），规则 ID 与用例一一对应。此后改规则 = 改 YAML + 加用例 + 跑回归，不再改动提示词。

---

## 五、维护约定（建议写进团队规范）

1. **一个事实源**：规则只在本文件；禁止在文末追加"补充说明""最高优先级"补丁段。历史上 16 处负面列举就是这么长出来的。
2. **新增驳回条件必须先改法务规则**，并同时加一条用例；否则新场景默认进风险报告，不构成驳回。
3. **变更必须引用规则 ID**：PR/工单写"改 B3 的大写校验，影响 X 单，用例 Y 已更新"。
4. **禁止在提示词里写日期补丁**（"以 2026-10-13 为准"），改为 CHANGELOG 一行 + 规则 ID 的 `effective_from`。
5. **回滚靠版本**：v3.0 整体可回滚，不做局部热改。
