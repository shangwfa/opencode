# Session skills 耗时现状与测量口径

## 当前结论

2026-10-04 本次只读检查：Docker 无运行容器；30040（OpenSandbox）和 26443（OrbStack Kubernetes API）无监听。暂无真实模型驱动的简单/复杂 skill 分阶段耗时数据，不能报告 PVC/snapshot 性能排名。

既有日志中的 145 项 Core 测试总耗时 3.76 秒、18 项 PG 测试 2.28 秒、6 项 HTTP 测试 3.73 秒仅是测试套件运行时间。沙箱 I/O 为桩，不是技能执行延迟。桩扫描 durationMs 也不能当真实扫描数据。

## 链路

1. 摘要发现：SessionContext 合成技能摘要供模型判断，不等于执行技能。
2. 加载：模型调用原生 skill 工具，先 Permission.assert，再 SessionSkills.get，最后按来源准备正文/资源；显式 prompt skills 附件走输入准备链路。
3. 触发：模型读到指令后决定后续工具调用；skill 本身不自动启动脚本，不存在独立 skill 执行引擎。
4. 执行：核心 executor 执行 shell、文件、MCP、子任务等；CodeMode 中的工具调用仍经核心执行边界。skill 自身保留 native 暴露。
5. 完成：必须检查任务产物、执行轨迹和持久化数据，而不只是 skill 工具返回成功。

## 实现带来的成本

- `skills.ts:192`：已有运行沙箱时，每次 collect 都等待远端 find，然后读取全量会话技能 PG 行并合并三源；get 不是按 ID 的单行查询。正文缓存不会免掉 find。
- `scan.ts:275`：目录命令 timeoutMs=10000，safe-read 可重试；不是整段扫描端到端 10 秒保证。最多读取 200 个定义，变化文件并发读取 8。
- `skills.ts:202`：无资源 session skill 不物化；有资源时，冷加载写正文、最多并发 8 写资源、最后写完成标记。热加载先读标记和正文，再并发 8 读全部资源并校验摘要。
- `skills.ts:248`、`context.ts:143`：上下文准备逐个恢复明确 allow 的资源型技能，技能间串行；代价可能与所有 allow 资源型技能总量相关，而非只与此次选中技能相关。
- `prompt.ts:70`：不同显式附件顺序准备，每个唯一 ID 各自 get；多个附件可能重复 find 和全量 PG 读取。
- global 来源保留宿主 prepare 行为，其资源在沙箱中的可达性尚未解决，不应与可执行 session bundle 混作等价样本。

## 建议测量矩阵（待实测，不是性能预测）

固定模型、仓库、平台镜像和权限策略，默认 code-mode 开启。每组区分 sandbox/global/session 来源，global 先验证资源可达性。

| 复杂度 | 固定样本 |
| --- | --- |
| 简单 | 纯指令、0 资源、1 次确定性工具调用 |
| 中等 | 5 个资源、固定输入与输出、3～5 次顺序工具调用 |
| 复杂 | 50 个资源、固定总字节数、10～20 次调用，含并发/子任务 |

环境：本地 PG + I/O 桩仅作服务基线；Docker SaaS + OpenSandbox PVC；Docker SaaS + OpenSandbox snapshot。每种真实环境分别测已运行冷缓存、已运行热缓存、沙箱首次创建、沙箱恢复。测试总技能数单独取 1/20/100，不能和单技能资源数混淆。

分段记录：admission、权限等待、发现扫描、PG、资源校验/写入、模型首输出、首次后续工具、实际工具执行、最终完成。分别报告端到端及扣除人工权限等待的耗时；不能直接相加重叠的并发 span。

建议热态每格至少 30 次，冷建箱/恢复单独重复采样，给出样本量、失败率、中位数、P95、范围、资源总字节数和模型轮次。P95 的小样本不作稳定结论。跨副本另列，不冒充单实例数据。

## 后续环境纠正

开始实测后核对 `docs/local-test-env.md` 确认：既有平台实际在远端 `172.18.32.15:30040`；本机 30040 是 TCP 转发，不依赖本地 Kubernetes。远端 TCP 可达，恢复转发后真实沙箱正常创建。因此此前本地 30040/26443 无监听只证明本地入口状态，不能证明远端平台不可用。临时启动用于核查的本地 Kubernetes 已停止，没有更换远端平台。

初次真实运行的最后 PG 断言存在测试脚本缺陷：`resources` 列是 text JSON，不是 Bun.SQL 自动解码的数组。已按真实存储类型 JSON.parse 后重跑；不得将该断言失败描述为资源持久化失败。
