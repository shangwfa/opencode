# 远端 K8s 快照增量能力实验（2026-10-03）

## 目的

判定远端 K8s 后端快照是**层增量**（只提交变化层，小改便宜）还是**全量**（每次完整 rootfs）——决定快照策略（周期检查点激进程度、CLEAN 复用的地位）。参照 Modal 内容寻址增量（行业研究 P1-1）。

## 方法

远端 API 无 size 字段，用代理指标：SaaS 生产链路单会话多代快照，测创建耗时（kill→ready）、恢复耗时（kill 后下一命令 wall）、同快照重复恢复（层缓存效应）。

## 数据

### 实验 1：5 代快照（基线 2 文件 → 安装依赖 +344MB → 小改 1 行 ×3，晚间时段）

| 代 | 内容变化 | 创建耗时 |
|---|---|---:|
| G1 | 2 文件 | 121.3s |
| G2 | +344MB | 109.0s |
| G3 | +1 行 | 109.8s |
| G4 | +1 行 | 111.0s |
| G5 | +1 行 | 115.8s |

恢复耗时：自基线 11.1s；自 G2(344MB) 12.9s；自 G3/G4(小改) 6.7/6.9s。

### 实验 2：同一大内容快照连续恢复 ×3

8.7s / 5.7s / 9.9s——无递减模式。

### 对照：上午 realdev 同平台数据

S0 空区 16.3s / S2 +344MB 32.4s / S3 +2 行 19.2s / S4 +30MB 25.2s。

## 结论

1. **无法确定性判定增量**。晚间时段创建耗时与内容量完全无关（~110s 固定），上午数据的内容相关性（32 vs 19s）被平台波动淹没；远端不暴露存储 size，黑盒观测到极限。
2. **确凿发现：远端快照性能波动巨大**。同场景基线快照上午 16.3s vs 晚间 121.3s（3-7 倍），固定开销主导。无论增量与否：
   - 快照 SLA 不可依赖固定值；`waitMs` 预算必须覆盖慢时段（900s 合理）
   - 销毁降级档（已实现）与创建重试（已实现）的价值被实测证实
3. **弱信号**：恢复耗时与快照内容正相关（12.9 vs 6.7s），且重复恢复无层缓存递减——不支持"便宜的链式增量 + 热层缓存"模型；若有层机制，固定合并/上传开销也占大头。CLEAN 复用（跳过创建）仍是当前最有效的成本控制手段，不能降级为兜底。
4. **确定性结论需要**：远端暴露快照 size 字段，或平台侧确认 snapshotter 类型（containerd native/overlayfs）。

## 边界

所有数据经 SaaS 生产链路（含 PG 仲裁/队列排队），非裸平台直连；晚间单时段样本；恢复耗时含调度。脚本见 `docs/test-cases/scripts/snapshot-incremental-e2e.mjs`、`snapshot-repeat-restore-e2e.mjs`。
