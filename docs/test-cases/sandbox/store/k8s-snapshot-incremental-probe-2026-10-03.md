## 目的

判定远端 K8s 后端快照是**层增量**（只提交变化层，小改便宜）还是**全量**（每次完整 rootfs）——决定快照策略（周期检查点激进程度、CLEAN 复用的地位）。参照 Modal 内容寻址增量（行业研究 P1-1）。

## 方法

远端 API 无 size 字段，用代理指标：SaaS 生产链路单会话多代快照，测创建耗时（kill→ready）、恢复耗时（kill 后下一命令 wall）、同快照重复恢复（层缓存效应）。

## 数据

### 实验 1：5 代快照（基线 2 文件 → 安装依赖 +344MB → 小改 1 行 ×3，晚间时段）

| 代 | 内容变化 | 历史端到端耗时（含重试） |
|---|---|---:|
| G1 | 2 文件 | 121.3s |
| G2 | +344MB | 109.0s |
| G3 | +1 行 | 109.8s |
| G4 | +1 行 | 111.0s |
| G5 | +1 行 | 115.8s |

恢复耗时：自基线 11.1s；自 G2(344MB) 12.9s；自 G3/G4(小改) 6.7/6.9s。

### 实验 2：同一大内容快照连续恢复 ×3

8.7s / 5.7s / 9.9s。仅三个样本且调度/缓存未知，不能据此排除缓存影响。

### 对照：上午 realdev 同平台数据

S0 空区 16.3s / S2 +344MB 32.4s / S3 +2 行 19.2s / S4 +30MB 25.2s。

## 结论

1. 历史五代耗时受到重试污染，不能据此确认平台时段性能波动，也不能用来验证 900 秒等待预算最优或销毁降级的数据保护语义。
2. 历史恢复耗时包含命令执行，首次恢复还包含依赖安装；不能把大小修改后的少量恢复样本作为增量或缓存模型的判断依据。
3. 已核验的 OpenSandbox 源码会对沙箱启动镜像的父层生成可写层 diff，而不是每次导出整个 rootfs；仍需确认远端部署版本。相对启动镜像的增量不等于相对上一检查点的增量。
4. 性能复测应先固定有效配置和耗时口径、检查 attempts，再报告样本分布。增量机制确认需要实际 committer 版本与 OCI 层 digest/size；只确认 snapshotter 名称不够。

## 边界

所有数据经 SaaS 生产链路（含 PG 仲裁/队列排队），非裸平台直连；晚间单时段样本；恢复耗时含调度。脚本见 `docs/test-cases/scripts/snapshot-incremental-e2e.mjs`、`snapshot-repeat-restore-e2e.mjs`。
