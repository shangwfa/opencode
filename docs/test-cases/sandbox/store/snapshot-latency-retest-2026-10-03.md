# 远端快照耗时复测：排除 wait=1 与 SaaS 操作退避（2026-10-03）

## 结果

修正有效等待配置为 900 秒后，3 轮共 21 个检查点全部通过、全部 SaaS 操作 `attempts=1`；其中 18 次新建快照、3 次 CLEAN 复用。21 条 shell 命令全部 exit=0，恢复后校验工作区普通文件 SHA-256，构建成功且 BUILD_ID 存在。3 个本轮会话通过 SaaS DELETE 清理，原始证据先保存。

常规端到端耗时：基线 12.46–16.58 秒，安装依赖后 33.27–45.77 秒，小改 12.45–25.86 秒，构建后第二/三轮约 25.85 秒；无变化复用 3.04–5.09 秒。第一轮构建后发生一次 **149.96 秒**异常，必须保留在结论中，不能只报告中位数。

**撤回旧结论：** 原 109–121 秒是受到 SaaS 重试污染的端到端测量，不是纯快照创建耗时，不能据此推断平台在该时段普遍变慢 3–7 倍。此次只改测试等待配置和验收脚本，未优化底层 commit 实现，不应描述为业务代码提速。

### 指标定义

1. **端到端**：发起 kill-sandbox → API 返回且 operation=done、PG sandbox=destroyed，被脚本观测到；含准备、仲裁、平台创建、SaaS 轮询与销毁。观测间隔 1 秒及网络耗时影响结果。
2. **PG 创建到 Ready**：`session_snapshot.time_updated - time_created`，在新快照 Ready、尚未恢复前取值；创建行在平台 create 返回后插入，故不是完整平台创建过程，还包含 SaaS 5 秒轮询感知。
3. **平台记录创建→Ready**：平台 `createdAt` 到 Ready `status.lastTransitionAt`。已核验本地平台源码是在 inspect/reconcile 发现 Ready 时记录 transition 时间，因此它是平台服务记录的完成耗时，包含 Job/生成/上传/状态发现，**不是纯 diff、压缩或 commit 的耗时**。远端部署源码版本仍未确认。

脚本每约 1 秒只读查询平台状态，该查询可能触发平台状态 reconciliation，平台记录时间受此观测方式影响；所有三轮采用相同方法。它不改变 SaaS 的固定 5 秒轮询，不代表改变了底层 commit 算法。

- 平台 Ready transition：`2026-10-03T02:59:35.446781Z`，差 **144.20 秒**。

可下结论：异常主要发生在平台请求被接受后的完成/状态可见链路，不是本次 SaaS 操作指数退避。不可下结论：到底是 Pod 启动、拉镜像、平台内部 Job 重试、CPU/磁盘、Registry 上传还是 controller/status 延迟。SaaS attempts=1 不排除平台内部重试；需要远端 Job events 和 committer 阶段日志才能定位。

## 修正后的结论与优化方向

1. 常规创建不是稳定 110 秒，当前样本约基线 12–17 秒、依赖 33–46 秒、小改 12–26 秒。工作量差异在本轮重新可见，但不凭耗时证明增量机制。
2. 平台长尾确实在本轮发生过一次；不能宣称“平台没有慢请求”，也不能用单次异常推断常态 SLA。3 轮样本不足以估计生产长尾概率。
3. CLEAN 本轮 3 次均未创建快照且仅耗时 3–5 秒，继续是减少新建次数的有效机制，独立于底层是否增量。
4. 先保持正常等待配置，避免 Creating 被极短 wait 放大为退避；分开统计受理、平台完成、SaaS Ready 感知和 API 完成。
5. 端到端中位数比平台记录中位数多约 4–8 秒，但两类时钟/观测口径和阶段不同，不能将差值全部视为可消除的轮询开销。后续需分阶段指标才能选择优化点。
6. 当前重点仍是平台长尾定位及扫描/轮询优化。下一项增量研究应比较“同一个活跃沙箱连续 refresh”与“每次恢复后快照”，本轮后者不能替代前者。
7. 900 秒只是恢复代码默认等待预算并用于排除这次测试污染，没有证明该值最优；任何快照失败自动销毁脏源沙箱的旧快照降级也不能由本次性能结果证明安全。
