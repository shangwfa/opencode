# 统一自动化应用方案（设计稿）

因此核心取舍不是复刻影刀的桌面开发器，而是借鉴其**单应用、先发版再运行、运行与调试分离、可观察可恢复**的心智模型：让 AI 帮用户完成原本需人工搭建的流程，正式运行仍是可审计的固定动作。

## 一、产品定义与边界

只有一种面向用户的「自动化应用」：**设计时 AI 协作，运行时固定流程，异常时 AI 辅助修复**。用户看到业务目标、输入、阶段、结果与运行记录；脚本、选择器、模型和沙箱是可展开的实现细节，不是另一类应用。

| 阶段 | AI 的职责 | 运行与用户动作 |
| --- | --- | --- |
| 讨论/探索 | 与用户澄清目标、例外、参数、敏感操作、验收条件；在授权的沙箱/网页中探索 | AI 可调用工具，探索过程明确标为“设计中”，不能视为正式应用运行 |
| 生成/测试 | 从已验证证据生成业务步骤 + 固定动作候选；失败时提出局部修复 | 草稿可审阅、逐步试跑、核对产物；修复必须应用后重测；完整通过才可发布 |
| 已发布运行 | **正常路径不调用模型** | 输入参数、选择工作区、启动；执行器按版本快照直接顺序执行固定网页动作/脚本，展示进度、结果与证据 |
| 异常恢复 | 仅对确定失败的当前步骤提出局部修复建议 | 先检查部分副作用；用户审核后只从失败处继续；不重放已成功步骤；连接中断、超时及结果不确定时禁止自动重试 |
| 升级应用 | 可解释修复原因并提出新版本 | 本次运行成功不自动修改已发布版本；核对结果、完成必要的回归测试后明确发布新版本 |

不把“AI 作为每个业务步骤的默认执行器”带进新应用。保留旧版的**业务语言、参数、结果校验、会话讨论和低门槛生成**，不保留其每步模型调用的常态运行模式。

## 二、一个应用，业务层与执行层并存

以现有 `automation_app` / `automation_draft` / `automation_run` 为目标持久化模型，不再为新应用写入 `instruction_*`。每个应用的发布版本是不可变的执行快照，至少包括：

- 业务层：名称、用途、输入参数（类型/必填/默认值/校验）、按用户语义分组的阶段；每阶段包含目标、成功判据、可能的人工介入说明。
- 执行层：每阶段对应有序固定动作（现有 browser navigate/fill/click/wait/extract 与 sandbox python/javascript），脚本资源、输出引用、步骤间数据契约；参数只通过结构化输入传递，不拼入代码或选择器。
- 验收层：每阶段可检查的断言（例如提取值、文件存在及内容、业务状态），最终产物及通过条件；**不能只凭退出码 0 或模型说“完成”就算通过**。旧版 `verification` 是可复用起点。
- 安全层：动作风险等级与确认策略、允许的工作区/网络/副作用范围、凭据使用边界；版本哈希、测试证据、发布人和时间。默认对尚未审核的点击/脚本保守确认；只有明确标注并验证为低风险的动作才可免逐步确认，高风险动作每次仍要确认。
- 溯源：探索会话、来源记录/定位证据、草稿版本、测试运行 ID、修复版本；不把会话文字直接当可执行代码。

业务层供普通用户阅读与修改，执行层供高级用户展开审核。业务目标变更会使相关执行动作及验证证据失效，必须重新测试。暂不在没有可验证操作的步骤中加入“运行时 AI 补全”回退；不可执行的草稿不能发布。

## 三、界面与交互

1. **一个列表/详情入口** `/cdp/apps`；列表可按状态筛选“设计中 / 待测试 / 已发布 / 待迁移”，不按技术实现拆成两个产品。卡片强调业务名称、最近运行结果、版本和运行方式；不以“AI 执行”作为新应用类别。
2. “创建应用”进入带会话的设计台：聊天澄清需求 → AI 探索 → 业务步骤和固定动作并排审阅 → 用户修改参数/验收标准 → 沙箱试跑 → 发布。可以从现有任务记录导入，不要求用户编写 RPA 脚本。
3. 已发布详情是运行台：参数、运行按钮、业务阶段时间线、异常处理、产物与历史；底层动作默认折叠。设计/修改走“编辑新草稿”，不会在运行页静默修改当前版本。
   运行记录至少可按时间、版本、结果和触发方式筛选，并能查看每步输入/输出摘要、错误、产物链接；用户可从失败记录一键进入带上下文的修复草稿。
4. 失败态显示“已完成/当前失败/未开始”、错误证据、可能的部分结果，以及“让 AI 提出修复”“人工接管”“停止”。修复方案给出变更对比；审核后继续的是**本次运行快照**，不直接更新应用。完成后另有“验证并发布修复版本”。
5. 旧链接 `/cdp/instruction-apps/:id` 和既有运行历史可读，并导向统一详情的“待迁移”视图；旧版不是第二个主导航。已发布旧应用只显示真实能力，不伪装为固定流程。

## 四、执行、AI 修复和多 Pod 状态

- 运行以 PG 中的应用版本快照与 `requestKey` 创建；worker 以 PG 行状态 + advisory lock 认领，逐步持久化检查点。会话→沙箱从 PG 读取；文件/命令走 OpenSandbox 控制面，不依赖 pod 与沙箱亲和性。
- 启动时对已审阅的固定脚本作一次运行授权；低风险、已验证动作顺序执行。每个真正高风险动作单独暂停（付款、发货、删除、外部提交等）；不能只凭 CSS 或按钮文案由 AI 自行推断“安全”。
- 对确定性定位失败可以建议修复选择器；对确定性脚本失败可以建议修复代码；AI 只产候选，不可绕开确认、扩展授权范围、读新凭据或隐式外发。修复次数有上限；修复后只继续当前步骤及后续步骤。
- 命令已派发但网络断开、超时、浏览器页面可能已点击、文件可能已部分写入等均进入 `uncertain`，需核查/人工决定；不得“恢复时重放”。副作用步骤尽可能使用业务幂等键、产物原子写入及可核对的完成标记，但不以此替代人工核实。
- 升版必须完成运行结果验证 + 版本 CAS + 审计。并发中的旧运行仍按自身快照执行，不被新版本改写。草稿修复仍采用“应用修复 → 重测 → 发布”门槛。
- 当前前端对 `automation_run` 轮询提供阶段状态；建议补运行级 SSE（或订阅 PG 驱动的服务端事件）推送业务阶段/暂停/产物。会话 SSE 只用于**设计阶段或异常 AI 修复阶段**的模型过程，不能将其“无模型事件”误当作运行进度。
- 后续扩展触发器/调度时，它们只引用已发布 `appId + version` 或明确的“最新发布版本”策略；须定义排队/拒绝冲突与运行身份、确认/审批通道。无人值守任务遇高风险动作或不确定结果必须暂停、告警，不能由触发器静默批准。

## 五、旧应用迁移与兼容策略

当前两套 PG 表、运行器和 API 确实独立：`instruction_*` 的定义只有文字指令/结果校验，`automation_*` 的定义含固定动作/脚本；直接改表名或把 `instructions` 填进 `steps` 会造出不可运行的应用。因此分期迁移，禁止“静默转换成功”：

1. 新建与新发布只走统一草稿/应用契约，停止生成新的指令型应用。已有 `instruction_app` 和 `instruction_run` 原样保留，历史输出与审计可查。
2. 旧应用显示“待迁移（原运行方式逐步调用 AI）”。用户选“升级为固定流程”：加载旧业务步骤、参数、校验条件和关联的实际成功会话记录，由 AI 生成**候选**固定动作；定位/脚本无证据时要求补充探索，不猜测。记录 `legacyAppId → 新草稿/新应用 ID`，迁移幂等。
3. 对候选先在隔离会话试跑，核对结果/产物和危险动作，再发布统一应用的新版本。迁移前不得谎称旧应用“直接执行脚本”。旧版运行可在过渡期从旧详情以明确提示和单独授权继续使用，**默认的新建与主路径不再使用旧运行器**；确认存量业务迁移后再停止旧运行入口，最后移除旧 worker/API 和表。
4. 过渡期应用列表按 owner 聚合两套表；同一旧应用成功迁移后默认只显示新应用，旧记录通过“迁移来源/历史运行”可查，避免一项业务重复成两张活跃卡。不能删旧表/旧运行记录，不能丢失旧 URL 的跳转能力。

## 六、实施顺序与验收门槛

**阶段 A｜契约和入口统一。** 明确统一应用状态机、业务层/执行层/验收层及风险标记；统一列表、详情和创建入口；旧链接兼容。测试：新旧查询权限、重复卡去重、旧运行历史可见。

**阶段 B｜AI 协作设计闭环。** 同一设计台支持讨论、从成功记录生成候选、审阅和修改、草稿测试、修复重测、发布；证据不足拒绝。测试：无证据不编脚本、并发导入幂等、发布版本及测试哈希一致。

**阶段 C｜运行与修复闭环。** 补步骤级断言、明确风险确认策略和运行级事件；异常分确定失败/结果不确定，修复只作用于本次运行，升版需复核。测试：正常运行不调模型、异常仅一次局部修复、前序不重跑、部分副作用与断线不自动重放、并发版本不覆盖。

**阶段 D｜存量迁移与退役。** 建映射及迁移任务，逐个从旧业务指令生成并验证新固定流程；存量逐步迁移后再关旧执行入口。测试：迁移幂等、旧链接/历史只读、迁移失败无影响、无重复活跃卡、迁移后固定运行输出一致。

**阶段 E｜规模化运行（后续）。** 在同一发布版本上接定时/Webhook/API 调度、共享权限和运行告警；单独验证排队、幂等、鉴权与无人值守高风险暂停，不为此恢复“每步 AI 执行”。

每阶段需通过单测与真实接口 E2E（`demo@example.com`、SaaS Docker + OpenSandbox + PG）：检查用户界面、步骤状态/耗时、产物、PG 的版本/快照/审计；涉及 AI 的设计和修复期间订阅会话 SSE 并实时呈现思考/工具/表单；正常固定运行检查运行事件且确认没有逐步模型 prompt。发现优化问题先沉淀可复现用例。

实施进度（部分完成，非整体验收）：统一入口、旧成功运行生成固定草稿、独立产物校验及详情页单份步骤状态列表已有实现和模拟 SaaS + 真实 PG 测试；旧运行证据按游标跨页读取每步 prompt 和完成消息。真实迁移的 AI 生成→测试→发布及会话 SSE 闭环尚未验收；迁移生成目前同步等待模型，慢模型可能超过网关超时，需改为 PG 持久化异步任务或验证端到端超时后才可视为可用。风险分级、运行级事件及旧应用退役仍在后续阶段。

## 七、需要产品确认的两处策略

1. 旧版应用过渡期是否允许在旧详情页显式授权继续按 AI 方式运行？建议允许已有用户短期继续，但统一入口只推荐“升级为固定流程”，设置可观测的迁移进度与退役门槛；不允许创建新的旧版应用。
2. 已验证低风险网页点击是否允许像传统 RPA 一样免逐步确认？建议允许，但必须在设计/测试时显式标注并审核风险；未分类和高风险动作继续逐步确认。现有实现对**所有**点击都会暂停，需单独改造，不能仅改文案。
