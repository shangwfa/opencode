# 知识库产品形态：一个资产，三个通道

> 2026-10-26 · 讨论稿，不含实现

## 一句话定位

**知识库不是文档站，而是可以被"读、被编辑、被调用"的资产。**

同一个知识库同时是：

- 人写的内容（文档 / 数据表）
- 机器用的知识（索引 / 图谱 / Wiki）
- 对外的能力（站点 / API / MCP / 文档 Agent）

作者和读者不是两类人，是**同一批人在不同通道上的不同权限**。

## 现在为什么别扭

1. **编辑通道借住在站点里**：为读者设计的目录、面包屑、阅读排版，被迫承担写作；建文档藏在"更多"，状态看不见。
2. **内容与产物混在一个"库"里**：文档、分块、向量、图谱、Wiki、数据表平铺，用户看不出"我的知识现在能不能被 AI 用"。
3. **只有发布动作，没有发布结果**：点"发布"之后，站点何时生效、AI 何时能查到、失败了怎么办，界面答不出来。

## 对象模型

```
Workspace（个人 / 组织）
└── Knowledge Base（有主、有成员、有策略的知识资产）
    ├── Source        内容源
    │   ├── Documents      文档树（草稿 / 发布 / 版本）
    │   ├── DataTables     结构化数据（表 + 字段 + 行）
    │   └── Feeds          外部同步（仓库、站点、API）
    ├── Compile       编译产物（可重建、会失败）
    │   ├── Index          分块 / 向量 / 关键词
    │   ├── Graph          实体 / 关系
    │   └── Wiki           概念 / 修订
    ├── Release       版本（不可变快照）
    └── Channels      出口
        ├── Site           只读站点
        ├── API            REST（OpenAPI）
        ├── MCP           工具服务器
        └── Agent          文档型智能体
```

关键规则：

- **Source 是人维护的**，可编辑、可回滚，单一真相。
- **Compile 是可丢弃的**，任何时候都能从某个 Release 重建。
- **Release 是不可变的**：一旦生成，站点、API、Agent 都指向它。
- **Channels 只是指针**：切换/回滚 = 改指针，不改数据。

## Release：一个动作，多个产物

发布不是"改一个字段"，而是生成一个版本：

```
草稿 ──publish──▶ Release v12
                   ├── site snapshot      （秒级生效）
                   ├── index snapshot     （异步，可失败可重试）
                   ├── graph / wiki       （可选，独立进度）
                   └── manifest           （对外契约，含版本号）
```

界面必须永远能回答三句话：

1. **线上站点现在是什么版本？**
2. **AI 现在能检索到哪个版本？**
3. **哪个环节失败了，重试会影响谁？**

> 单篇发布保留，但落地为单位是"生成新 Release"。站点和索引允许短暂不同步，但要显式显示差集。

## 通道一：站点

- 只读、可分享、可自定义域名（后续）。
- 可发布到：私有（仅成员）/ 组织内 / 链接可读 / 完全公开。
- 站点有 **preview 通道**：指向草稿 Release，给作者和评审看，不进公开。

## 通道二：API 与 MCP（同一份契约）

**一份 manifest，多协议出口**，避免 OpenAPI 与 MCP 工具各写一套而后漂移。

```jsonc
// kb://product-help/manifest@v12
{
  "version": "v12",
  "tools": [
    { "name": "search",        "scope": "kb.read",  "schema": { "query": "string", "topK": "int?" } },
    { "name": "get_document",  "scope": "kb.read",  "schema": { "docId": "string" } },
    { "name": "ask",           "scope": "kb.ask",   "schema": { "question": "string" }, "citations": "required" },
    { "name": "graph_query",   "scope": "kb.graph", "schema": { "entity": "string" } }
  ],
  "limits": { "rpm": 60, "dailyTokens": 200000 }
}
```

- **REST**：`/v1/search`、`/v1/ask`、`/v1/documents/:id`，OpenAPI 由 manifest 生成。
- **MCP**：同一 manifest 生成工具列表，走 Streamable HTTP。
- **凭证**：知识库级 token，可作用域（只读 / 可问 / 可图）、可限额、可轮换、可审计。
- **复用**：连接器已有「应用级 MCP + token 哈希 + 工具白名单 + 配额」，把这套机制平移到知识库，不新造。

**关键差异（相对普通 API）**：知识 API 的返回值必须带**引用**（文档 + 块 + 版本），否则使用者无法判断可信度。

## 通道三：文档型 Agent

不是"给个 prompt 让它答"，而是一个**有配置、可评测、可发布的资产**：

| 配置项 | 说明 |
|---|---|
| 知识范围 | 绑定一个或多个 Release（可跨库） |
| 工具子集 | 只用 manifest 里的哪些工具 |
| 检索策略 | topK、rerank、是否 HyDE、时间衰减 |
| 回答约束 | 必须引用、无依据时拒答、禁止外推 |
| 人设 | 语气、术语表、免责声明 |
| 出口 | 站点浮窗 / 独立链接 / API / IM |
| 评测集 | 20–50 个问题 + 期望要点 |

**发布前门禁**：跑评测集，命中率 / 引用率 / 拒答正确率达标才允许上线。这是把"AI 答得好不好"从感觉变成数字。

## 通道四：OpenCode 会话（自家 Agent，最重要的消费者）

前面的通道是"对外"；这一条是"对内"——**知识库是 SDK 级基础能力，不是一个要去手动挂的插件**。

### 1. 自动解析，不手动挂载

会话不配置 KB，而是按三层解析，越具体越优先：

```
组织默认知识库 → 应用/项目绑定 → 需求/会话覆盖
```

例：这个需求属于 `product-help` 应用，就用该应用绑定的库；没有绑定就落组织默认。**用户不需要知道"知识库"这个对象存在。**

### 2. 会话 MCP，复用现有机制

已经有的两部分可以直接拼上：

- 会话级 MCP（`POST /api/sessions/:id/mcp` + supergateway 桥）
- 知识服务里已有的工具体与 MCP 适配（文档检索、多库检索、统一检索、图谱查询、Wiki 查询）

于是"知识库给会话当基础能力"= 会话启动时按绑定声明一个 MCP，工具面由该库的 **manifest** 生成。

### 3. 工具面分三层，按成本递进

| 层 | 工具 | 成本 | 何时用 |
|---|---|---|---|
| 轻 | `kb_search` | 一次检索 | 定位候选 |
| 中 | `kb_get_document` / `kb_get_block` | 读全文/块 | 需要细节 |
| 重 | `kb_ask`（含 rerank / 多跳） | LLM + 检索 | 需要综合回答 |

Agent 先用轻的，需要才升级——**上下文是最贵的资源，不是 token 越少越好，而是"按需付费"**。

### 4. 引用与可复现：会话钉住 Release

会话启动时钉住一个 `Release`（如 `v12`），之后所有引用都带 `(docId, blockId, release)`。

好处：

- 回答可复现：同一条消息永远能追到当时的正文
- 内容更新不影响进行中的会话
- 前端能把引用渲染成可点击、可跳原文的锚点

### 5. 计量按会话归属

每次检索/问答记录：`sessionId`、`requirementId`、`kbId`、`release`、tokens、耗时。

于是能回答："这个需求花了多少知识检索成本"、"哪个库最常被 Agent 调用"。

### 6. 让会话反向产出知识

这是闭环的另一半：

```
会话里解决了值得记录的问题
        ↓
Agent 生成「文档草稿提案」（标题 + 正文 + 来源消息）
        ↓
人在工作台审阅（diff）
        ↓
合入 → 发布 → 新 Release → 下次会话能用上
```

默认**只能产出草稿，不能直接发布**；需要显式授权。这样 Agent 既是消费者也是贡献者，但不会污染知识库。

### 7. 边界

- 知识库与应用/租户绑定，会话不得跨租户检索
- 工具调用受 manifest 的 scope 与配额约束
- 无依据必须拒答，不允许用模型常识补齐

## 闭环：读者与 Agent 的问题都变成作者的待办

这是我认为最有价值的一环（会话侧同样适用）：

```
用户提问 → 检索 → 回答（带引用）
              │
              ├─ 命中：记录「哪些块被引用最多」→ 作者知道哪篇最重要
              └─ 未命中 / 低分 / 被拒答
                        ↓
                   Content Gap（知识缺口）
                        ↓
             待办：补文档 / 补数据表 / 拆分过长文档
                        ↓
                   写 → 发布新 Release
```

于是"知识维护"不再是凭感觉补文档，而是**有排期的、由真实问题驱动的**。

配套两个指标：

- **覆盖率**：近 7 天问题中有依据回答的比例
- **新鲜度**：最常被引用的块里，超过 N 天未更新的比例

## 权限矩阵

能力而不是角色决定界面。角色只是能力的预设包。

| 能力 | 拥有者 | 编辑 | 读者 | API 使用者 |
|---|---|---|---|---|
| 读文档 / 搜索 | ✓ | ✓ | ✓ | ✓（scope） |
| 新建 / 编辑草稿 | ✓ | ✓ | — | — |
| 发布 / 回滚 | ✓ | 可选 | — | — |
| 管理成员 | ✓ | — | — | — |
| 管理公开范围 | ✓ | — | — | — |
| 签发 API token | ✓ | — | — | — |
| 查看使用与缺口 | ✓ | ✓ | — | 仅自己的调用 |

**同一页面按权限渲染**：有 write 就看到编辑入口，没有就只剩阅读。不做"作者端 / 读者端"两套应用。

## 分阶段

**P0｜把地基摆正**（1–2 周量级）

- Release 对象落地：站点版本 + 索引版本 + 失败重试
- 一个编辑入口：目录 + 文档列表 + 状态 + 草稿/发布
- 隐藏未实现能力（图谱、Wiki、结构化导入），不摆配置表演
- 权限按能力渲染，不做两套界面

**P1｜开放能力**

- manifest 驱动 REST + MCP，知识库级 token（复用连接器机制）
- 引用返回（文档 + 块 + 版本）
- 使用统计：调用量、命中率、Top 引用块
- **会话自动接入**：组织/应用/需求三层解析 + 会话钉住 Release + 三层工具面（search → get → ask）

**P2｜智能化**

- 文档型 Agent：配置 + 评测 + 发布门禁
- Content Gap：未命中问题 → 维护待办（站点提问与 Agent 提问合并计算）
- 知识健康度：覆盖率、新鲜度、冲突检测
- **会话反向产出**：Agent 生成草稿提案 → 人审 diff → 发布

## 明确不做（避免过度设计）

- 图谱可视化编辑器（图谱派生还没真跑通，先不做画布）
- 多人实时协同光标（先做「谁在编辑」的锁与提示）
- 自定义域名、主题市场（P2 之后）
- 跨库联邦检索（先把单库做好）
- 数据表关系建模 UI（先支持导入 + NL 查询）

## 需要拍板

1. **Release 粒度**：以知识库整体发版（推荐），还是允许单篇独立发版？
2. **公开档位**：私有 / 组织 / 链接可读 / 完全公开，先做哪两档？
3. **凭证是否与连接器共用**：我建议共用同一套 token 体系，避免两套配额与审计。
4. **编辑入口宿主**：工作台内做编辑工作台（推荐），还是继续在文档站里加"作者视角"？
5. **会话默认接入方式**：组织默认自动挂载（推荐，用户无感），还是每个会话手动选择？
6. **Agent 能否写草稿**：默认关闭（推荐）还是默认开启提案？

## 从现状到目标的最小一步

不动 UI，先做三件事：

1. 引入 Release 概念（数据模型 + 一个"当前线上版本"字段）。
2. 发布时同时记录站点版本与索引版本，失败可单独重试。
3. 把"知识管理"页改成只回答那三句话：线上是什么、AI 能查什么、哪里失败。

这三步做完，"产品形态不理想"的大部分痛感会先消失，再谈 Agent 与开放能力。
