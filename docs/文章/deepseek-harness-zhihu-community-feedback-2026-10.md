## 回答本身的核心信息（答主自述）

- 该版本的 **Claude Code Mods 兼容层**属于 alpha 中的**实验性功能**，不保证 100% 兼容；详细兼容情况见仓库文档 `docs/subsystems/claude-code-mods.zh.md`。
- 做兼容层的**目的**：验证 Claude Code Mods 对插件作者提供的扩展能力，是否大致是 DSH"一切皆插件"架构能力的**子集**。
- **核心理念——"一切皆插件"**，从立项之初即确立（类比"开源"理念）。三方面意义：
  1. **满足多样化用户需求**：用插件+社区方式让每人用上最适合自己的 Harness；配合模型训练达到"言出法随"效果。"创造模式"已允许 Agent 自行编写并安装插件。
  2. **满足企业行业部署**：行业类 DSH 插件往往不公开，符合并受支持于 MIT 开源协议。
  3. **推进"Agent 自进化"**：Cordis 提供理论与工程基础，但仍需以新方式训练大模型，让模型知道可以改变自身、自我迭代。
- 团队正在招募"既懂大模型研究训练、又懂模型与 Harness 共同进化"的研究员。
- 判断标准：做"和其它 Harness 从技术理念到用户体验都差不多的产品"不是推进 AGI；推进 AGI 一定是**创新**的事。

## 对本项目的启示（opencode SaaS）

1. **插件/技能市场的透明化是共识痛点**：多个高赞评论指向"安装不透明、不知道装到哪、如何升级/卸载、版本兼容"。我们的 session-skills 已有资源 digest 校验、损坏修复、完成标记的基础，可差异化做到**安装位置与版本透明、可审计卸载、资源完整性校验、typosquatting 防护**。
2. **API 稳定性 vs 演进速度是核心矛盾**：社区对破坏性变更敏感，期望 **API 分级 / 官方适配层 / 限时兼容窗口**。值得在产品设计层面沉淀为"稳定 API + 实验 API"分层，并对破坏性变更给出过渡期与迁移工具。
3. **插件管理应与主进程解耦、支持回滚**：崩溃时不至于连带 DSH 一起打不开；热重载借鉴 **AB 分区 / 快照回滚**（与我们沙箱 snapshot 能力可直接呼应）。
4. **"整合包/组合清单"是真实需求**：创猿er（252 赞）的 DSH-PackForge 与 koishi 实践表明，**插件有序组合 + skills/预设打包 + 环境迁移**比单插件更重要，可作为我们技能/配置分发的一个方向。
5. **computer use、移动端、TUI/CLI、undo、会话间协作** 是社区明确的功能期待，可作为能力扩展路线图输入。
6. **生态活跃度高**：大量第三方项目自荐（PackForge、harness-action、DSHBox、HDSL、dsh-spawn、dsh-em-agent 等），说明插件作者群体已形成，配套的审核/推荐/分发基础设施价值大。
